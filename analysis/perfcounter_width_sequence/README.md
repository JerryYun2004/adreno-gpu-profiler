# Perf-Counter Width-Sequence Analysis

This directory contains offline analysis utilities for width-sequence experiments
captured by the Adreno perf-counter sweeper.

The scripts analyze how hardware counter totals change as the benchmark width
increases, typically across:

```text
128, 256, 512, 1024, 2048
```

Their main use is to identify counters that:

- scale strongly with input width;
- remain flat or saturate;
- stay at zero across all widths;
- show stable behavior across repeated sweeps; or
- suggest growing pressure in SP, TP, UCHE, HLSQ, RBBM, CP, or related GPU
  blocks.

Unlike the KGSL trace-analysis utilities, these scripts are closely connected to
the project’s main perf-counter tooling.

- `tools/profiling/perfcounter_sweeper/` produces the multi-group, multi-chunk
  CSV captures analyzed here.
- `tools/profiling/perfcounter_streamer/` uses the same underlying counter access
  path, but these scripts are primarily designed around sweeper directory
  layouts rather than one standalone streamer CSV.

---

## Status and relationship to the main tools

| Script | Status | Main role | Relationship to streamer/sweeper |
|---|---|---|---|
| `analyze_repeated_width_sweeps.py` | Recommended primary analyzer | Repeated sweeps using one reference CSV per run | Direct post-processing for sweeper output |
| `analyze_repeated_width_sweeps_local_windows.py` | Recommended validation/alternative analyzer | Repeated sweeps with independently detected windows in each CSV | Direct post-processing for sweeper output |
| `analyze_width_sequence_ref_windows.py` | Reusable single-run analyzer | One sweep using a reference CSV to define width windows | Direct post-processing for one sweeper run |
| `analyze_width_sequence.py` | Legacy exploratory analyzer | One sweep with local detection and whole-file fallback | Older direct post-processing path |
| `make_repro_report.py` | Experiment-specific report generator | Produces a Markdown report for repeated fused-softmax runs | Consumes outputs from the repeated reference-window analyzer |

The recommended default workflow is:

```text
streamer_sweeper capture
        ↓
analyze_repeated_width_sweeps.py
        ↓
make_repro_report.py
```

Use `analyze_repeated_width_sweeps_local_windows.py` as an independent check
when a shared reference window may be unreliable.

# Expected input layout

## One sweep

A typical sweep directory looks like:

```text
sweep_20260625_174559/
├── 01_CP/
│   ├── CP_chunk001.csv
│   ├── CP_chunk001_benchmark.log
│   ├── CP_chunk001_meta.txt
│   └── ...
├── 02_RBBM/
├── 03_PC/
├── 04_VFD/
├── 05_HLSQ/
├── 06_VPC/
├── 07_TSE/
├── 08_RAS/
├── 09_UCHE/
├── 10_TP/
├── 11_SP/
│   ├── SP_chunk001.csv
│   └── ...
├── 12_RB/
├── 13_LRZ/
├── 14_ALWAYSON/
├── run_config.txt
└── summary.csv
```

The exact set and numbering of groups can vary.

Each chunk CSV should contain:

```text
elapsed_s,<counter_1>,<counter_2>,...
```

For example:

```text
elapsed_s,SP_BUSY_CYCLES,SP_ALU_WORKING_CYCLES
0.000000,0,0
0.001023,0,0
...
```

The analysis scripts treat every column except `elapsed_s` as a hardware counter.

## Repeated sweeps

The repeated-run scripts expect a root directory containing directories named:

```text
sweep_*
```

For example:

```text
results/perfcounter_sweeps/full_sweeps/
├── sweep_20260624_124835/
├── sweep_20260624_145250/
├── sweep_20260624_145305/
├── sweep_20260625_130734/
├── sweep_20260625_152944/
└── sweep_20260625_174559/
```

Only direct child directories matching `sweep_*` are discovered.

## Reference CSV

The reference-window scripts detect all width regions from one CSV and apply the
resulting time windows to every other chunk in the same sweep.

The repeated-run default is:

```text
11_SP/SP_chunk001.csv
```

A good reference CSV should:

- contain visible activity in every width region;
- contain exactly the expected number of bursts after thresholding;
- have a valid `elapsed_s` column;
- span the same capture timeline as the other chunk CSVs; and
- avoid counters that remain zero for the entire run.

# Core analysis concepts

## Aggregate activity

For one CSV, aggregate activity at each sample is:

```text
sum(abs(counter_i))
```

across all counter columns.

This avoids depending on one exact counter name during region detection.

## Activity threshold

A sample is active when:

```text
activity > max(activity) × threshold_frac
```

The default threshold fraction is usually:

```text
0.08
```

or 8% of the maximum aggregate activity in the reference/local CSV.

## Region detection

The scripts:

1. mark active samples;
2. collect contiguous active regions;
3. merge regions separated by at most one sample;
4. keep the strongest expected number of regions if too many are found; and
5. require the final region count to match the number of widths.

Reference-window scripts fail or skip a run when this requirement is not met.
The older local single-run script can instead fall back to whole-file totals.

## Counter statistics

For every counter and width window, the scripts calculate:

- `total`
- `max`
- `mean`
- `active_mean`
- `active_samples`
- number of samples
- region start and end time

`active_mean` excludes samples equal to zero.

## Scaling classification

Counters are heuristically classified using:

```text
scaling ratio = total at final width / total at first width
```

and Pearson correlation between total and width.

Current labels are:

```text
zero_all_widths
strong_width_scaling
moderate_width_scaling
flat_or_saturated
active_mixed
```

The current thresholds are:

```text
strong:
    ratio > 8
    correlation > 0.7

moderate:
    ratio > 2
    correlation > 0.5

flat/saturated:
    ratio < 1.5
```

These labels are heuristics, not formal bottleneck diagnoses.

For the standard sequence:

```text
2048 / 128 = 16
```

so a stable ratio near 16 is evidence that the counter scales approximately with
the number of processed elements.

## Cross-run stability

Repeated-run scripts aggregate each `(group, counter)` across sweeps and compute:

- majority classification;
- label consistency;
- mean and standard deviation of the first-to-last ratio;
- ratio coefficient of variation;
- mean and standard deviation of width correlation;
- mean and standard deviation of totals at each width; and
- run count.

A counter is marked `stable_strong_scaling` when:

- the majority label is strong or moderate scaling;
- label consistency is at least 0.67;
- ratio coefficient of variation is at most 0.25, when available; and
- mean width correlation is at least 0.90, when available.

A counter is marked `near_16x_scaling` when:

```text
15 ≤ mean ratio ≤ 17
mean correlation ≥ 0.95
```

# Script reference

## 1. `analyze_repeated_width_sweeps.py`

## Purpose

This is the recommended primary analyzer for repeated width-sequence sweeps.

For each sweep, it:

1. opens a designated reference CSV;
2. detects the width windows from that CSV;
3. applies those windows by elapsed time to every chunk CSV;
4. summarizes every counter at every width;
5. classifies counters independently for each run; and
6. calculates cross-run stability.

## Why we need it

Use this script when the main goal is reproducibility.

A single sweep can contain:

- transient noise;
- thermal or frequency variation;
- sampling alignment differences;
- startup effects; or
- a one-off region-detection error.

Repeated-run analysis shows whether the same counters and counter families
consistently scale with width.

The shared reference-window approach is also useful because all counter chunks
inside one sweep are segmented using the same workload timing.

## Relationship to the main products

This script is directly connected to the perf-counter sweeper. It consumes the
sweeper’s group/chunk CSV hierarchy.

It does not call the streamer or sweeper binary at runtime. It is an offline
post-processing stage.

It is only indirectly related to the standalone streamer. A single streamer CSV
could use similar logic, but this script expects repeated sweeper directories
and chunk files.

## Inputs

```text
--sweeps-root       Root containing sweep_* directories
--out-dir           Output directory
--widths            Ordered comma-separated width list
--reference-relpath Reference CSV path inside every sweep
--threshold-frac    Detection threshold as fraction of maximum activity
--min-active-samples
--pad-samples
--latest-n          Analyze only the newest N sweeps; 0 means all
```

Defaults include:

```text
widths:             128,256,512,1024,2048
reference-relpath:  11_SP/SP_chunk001.csv
threshold-frac:     0.08
min-active-samples: 1
pad-samples:        20
latest-n:           0
```

## Recommended command

From the repository root:

```bash
python3 analysis/perfcounter_width_sequence/analyze_repeated_width_sweeps.py \
  --sweeps-root results/perfcounter_sweeps/full_sweeps \
  --latest-n 2 \
  --widths 128,256,512,1024,2048 \
  --reference-relpath 11_SP/SP_chunk001.csv \
  --out-dir results/perfcounter_analysis/repeated_width_sequence_latest2 \
  --threshold-frac 0.08 \
  --min-active-samples 1 \
  --pad-samples 20
```

Analyze all sweeps:

```bash
python3 analysis/perfcounter_width_sequence/analyze_repeated_width_sweeps.py \
  --sweeps-root results/perfcounter_sweeps/full_sweeps \
  --widths 128,256,512,1024,2048 \
  --out-dir results/perfcounter_analysis/repeated_width_sequence_all
```

## Outputs

```text
all_runs_counter_width_summary.csv
all_runs_counter_classification.csv
all_runs_reference_windows.csv
cross_run_stability_summary.csv
stable_width_scaling_counters.csv
stable_near_16x_counters.csv
stable_zero_counters.csv
```

## Main mechanisms and libraries

- `argparse`
- `pathlib.Path`
- pandas CSV loading, grouping, concatenation, and export
- NumPy arrays and reductions
- NumPy Pearson correlation through `np.corrcoef`
- linear trend slope through `np.polyfit`
- reference-based burst detection
- time-based window application
- per-run classification
- cross-run mean, standard deviation, and coefficient of variation

## Known limitations

- The reference CSV path must exist in every analyzed sweep.
- A run is skipped if the reference detects the wrong number of regions.
- Widths are assigned by region order.
- The reference timeline is assumed to align with all chunk CSVs.
- Only direct child directories matching `sweep_*` are discovered.
- “Latest” is based on directory modification time, which can change when files
  are copied or edited.
- Classification thresholds are fixed heuristics.
- `np.polyfit` slope is calculated but cross-run stability relies mainly on
  ratios and correlations.
- Counter totals can be affected by window padding and sampling interval.

## 2. `analyze_repeated_width_sweeps_local_windows.py`

## Purpose

Analyzes repeated sweeps while detecting width regions independently inside each
chunk CSV.

Unlike the reference-window analyzer, it does not assume that one SP CSV defines
the best timing for every other counter group.

It can optionally restrict analysis to selected groups.

## Why we need it

Use it as:

- an independent check of the reference-window method;
- a fallback when the reference CSV is missing or unreliable;
- a way to detect group-specific timing offsets;
- a quality audit for which groups/chunks contain detectable bursts; or
- a focused analysis of selected groups.

This script is particularly useful when some chunk captures start slightly
earlier or later than others.

## Relationship to the main products

It directly consumes perf-counter sweeper output and is a post-processing tool
for the sweeper.

It does not depend on the streamer or sweeper executable after the CSV files
have been produced.

## Inputs

```text
--sweeps-root
--out-dir
--widths
--latest-n
--threshold-frac
--min-active-samples
--pad-samples
--groups
```

Default groups:

```text
SP,TP,UCHE,HLSQ,RBBM,CP
```

## Recommended command

```bash
python3 analysis/perfcounter_width_sequence/analyze_repeated_width_sweeps_local_windows.py \
  --sweeps-root results/perfcounter_sweeps/full_sweeps \
  --latest-n 2 \
  --widths 128,256,512,1024,2048 \
  --out-dir results/perfcounter_analysis/repeated_width_sequence_latest2_local_windows \
  --threshold-frac 0.08 \
  --min-active-samples 1 \
  --pad-samples 10 \
  --groups SP,TP,UCHE,HLSQ,RBBM,CP
```

Analyze all available groups by explicitly listing them:

```bash
python3 analysis/perfcounter_width_sequence/analyze_repeated_width_sweeps_local_windows.py \
  --sweeps-root results/perfcounter_sweeps/full_sweeps \
  --widths 128,256,512,1024,2048 \
  --out-dir results/perfcounter_analysis/repeated_width_sequence_local_all \
  --groups CP,RBBM,PC,VFD,HLSQ,VPC,TSE,RAS,UCHE,TP,SP,RB,LRZ,ALWAYSON
```

## Outputs

```text
local_region_detection_quality.csv
local_width_windows.csv
all_runs_counter_width_summary.csv
all_runs_counter_classification.csv
cross_run_stability_summary.csv
stable_width_scaling_counters.csv
stable_near_16x_counters.csv
```

## Main mechanisms and libraries

- per-file aggregate activity
- independent local window detection
- configurable group filtering
- quality records for every examined CSV
- the same width-scaling and cross-run stability logic as the repeated
  reference-window analyzer

## Known limitations

- Different counters can receive slightly different width windows.
- Local detection can fail for sparse, flat, or zero-valued chunks.
- If too many candidate regions exist, only the strongest expected number are
  kept.
- Failed files produce quality records but no per-width counter rows.
- It does not write a `stable_zero_counters.csv` file.
- It calls classification even if no rows were successfully summarized; an
  entirely failed dataset can therefore cause a pandas grouping error.
- Comparing totals across files is less controlled than shared reference-window
  analysis because each file may use different boundaries.

## 3. `analyze_width_sequence_ref_windows.py`

## Purpose

Analyzes one width-sequence sweep using one user-selected reference CSV to define
the width windows.

This is the single-run counterpart of
`analyze_repeated_width_sweeps.py`.

## Why we need it

Use it when:

- testing a newly captured sweep;
- tuning threshold and padding settings;
- validating a candidate reference CSV;
- inspecting one run before launching repeated-run analysis; or
- generating a compact classification for one experiment.

It is useful during development because failures are immediate and easier to
debug than in a multi-run batch.

## Relationship to the main products

This script directly analyzes one perf-counter sweeper output directory.

It is not required to run the sweeper, but it is closely connected to its CSV
format.

## Inputs

```text
--sweep-dir
--reference-csv
--widths
--out-dir
--threshold-frac
--min-active-samples
--pad-samples
```

## Recommended command

```bash
python3 analysis/perfcounter_width_sequence/analyze_width_sequence_ref_windows.py \
  --sweep-dir results/perfcounter_sweeps/full_sweeps/sweep_20260625_174559 \
  --reference-csv results/perfcounter_sweeps/full_sweeps/sweep_20260625_174559/11_SP/SP_chunk001.csv \
  --widths 128,256,512,1024,2048 \
  --out-dir results/perfcounter_analysis/sweep_20260625_174559_ref_windows \
  --threshold-frac 0.08 \
  --min-active-samples 2 \
  --pad-samples 1
```

## Outputs

```text
reference_width_windows.csv
counter_width_summary.csv
counter_classification.csv
zero_counters.csv
width_scaling_counters.csv
flat_or_saturated_counters.csv
```

## Main mechanisms and libraries

- reference-based region detection
- time-based application of reference windows
- per-counter width totals
- first-to-last scaling ratio
- Pearson correlation against width
- linear slope through `np.polyfit`
- classification into zero/scaling/flat/mixed groups

## Known limitations

- Region detection raises an error if the reference does not produce exactly the
  expected number of regions.
- No cross-run reproducibility metrics are calculated.
- No explicit detection-quality CSV is produced beyond the reference window
  table and terminal output.
- `--reference-csv` is a full path, not a path relative to the sweep directory.
- The default padding is only one sample, which may be too narrow for low-rate
  captures.

## 4. `analyze_width_sequence.py`

## Purpose

This is the older exploratory single-sweep analyzer.

It detects active regions independently inside every chunk CSV and summarizes
the file without relying on a shared reference.

If region detection fails, it writes a whole-file fallback row with:

```text
width = -1
region_index = -1
detection_status = fallback_whole_file
```

## Status

Legacy but still useful for debugging.

The later reference-window and repeated-run scripts are generally better for
formal results because they use more controlled window boundaries and support
reproducibility analysis.

## Why we need it

Use it when:

- no reliable reference counter exists;
- checking which chunks visibly contain five bursts;
- diagnosing failed region detection;
- exploring a new sweep format; or
- obtaining whole-file fallback totals from problematic chunks.

## Relationship to the main products

It directly analyzes one perf-counter sweeper output directory.

It predates the more robust reference-window and repeated-run workflows.

## Inputs

```text
--sweep-dir
--widths
--out-dir
--threshold-frac
--min-active-samples
```

## Command

```bash
python3 analysis/perfcounter_width_sequence/analyze_width_sequence.py \
  --sweep-dir results/perfcounter_sweeps/full_sweeps/sweep_20260625_174559 \
  --widths 128,256,512,1024,2048 \
  --out-dir results/perfcounter_analysis/sweep_20260625_174559_local \
  --threshold-frac 0.08 \
  --min-active-samples 2
```

## Outputs

```text
counter_width_summary.csv
region_detection_quality.csv
counter_classification.csv
zero_counters.csv
strong_width_scaling_counters.csv
flat_or_saturated_counters.csv
```

## Main mechanisms and libraries

- local per-CSV activity detection
- one-sample-gap region merging
- strongest-region selection
- whole-file fallback
- quality reporting
- per-width counter aggregation and heuristic classification

## Known limitations

- Different chunks can use different windows.
- Fallback rows use width `-1` and are excluded from classification.
- If all files fail region detection, the classification output may be empty.
- It does not apply padding around detected regions.
- It cannot analyze repeated runs.
- Strong and moderate scaling counters are both written to a file named
  `strong_width_scaling_counters.csv`, which is slightly misleading.
- It is more sensitive to sparse or group-specific counter behavior than the
  reference-window approach.

## 5. `make_repro_report.py`

## Purpose

Generates a Markdown reproducibility report from the CSV outputs of
`analyze_repeated_width_sweeps.py`.

The report focuses on a repeated fused-softmax experiment and includes:

- reference windows;
- stable near-16x counters;
- memory/cache/TP/UCHE-related counters;
- selected key-counter values for every run; and
- a written interpretation.

## Status

Experiment-specific.

The script is useful for reproducing the original fused-softmax report, but it
is not yet a general reporting framework.

## Why we need it

Use it when converting detailed CSV outputs into a human-readable report for:

- supervisor updates;
- method documentation;
- experiment records;
- reproducibility checks; or
- comparison of key counter families.

## Relationship to the main products

It is two stages downstream from the sweeper:

```text
streamer_sweeper
    → analyze_repeated_width_sweeps.py
    → make_repro_report.py
```

It does not read raw sweeper CSV files directly.

## Required input files

The specified analysis directory must contain:

```text
cross_run_stability_summary.csv
all_runs_reference_windows.csv
all_runs_counter_classification.csv
```

These are produced by `analyze_repeated_width_sweeps.py`.

## Command

```bash
python3 analysis/perfcounter_width_sequence/make_repro_report.py \
  --analysis-dir results/perfcounter_analysis/repeated_width_sequence_latest2 \
  --out docs/ml_primitive_reports/fused_softmax_width_sequence_perfcounter_analysis.md
```

## Output

A Markdown report at the path passed through `--out`.

## Main mechanisms and libraries

- pandas filtering and sorting
- keyword-based counter selection
- fixed key-counter allowlist
- DataFrame-to-text tables
- Markdown generation
- experiment-specific interpretation text

## Current key-counter list

The script highlights counters including:

```text
SP_BUSY_CYCLES
SP_ALU_WORKING_CYCLES
SP_FULL_ALU_MUL_INSTRUCTIONS
SP_GM_STORE_INSTRUCTIONS
SP_UCHE_WRITE_TRANS
SP_STALL_CYCLES_TP
SP_LOW_EFFICIENCY_STARVED_BY_TP
UCHE_BUSY_CYCLES
UCHE_RAM_READ_REQ
UCHE_RAM_WRITE_REQ
UCHE_WRITE_REQUESTS_SP
UCHE_READ_REQUESTS_TP
UCHE_VBIF_LATENCY_CYCLES
TP_L1_CACHELINE_REQUESTS
TP_STARVE_CYCLES_UCHE
```

## Known limitations

- The report title and benchmark configuration are hard-coded for fused softmax.
- Width-specific columns are hard-coded to 128, 256, 512, 1024, and 2048.
- `total_w2048_mean` is assumed to exist.
- The reference window explanation is hard-coded to
  `11_SP/SP_chunk001.csv`.
- Counter keywords and key-counter names are fixed.
- It expects reference-window analysis output, not local-window output.
- Large DataFrames are rendered as plain text inside fenced code blocks.
- Missing expected CSV files or columns raise exceptions.

# Recommended workflows

## A. Analyze one new sweep

First use the reference-window single-run analyzer:

```bash
SWEEP="results/perfcounter_sweeps/full_sweeps/sweep_20260625_174559"

python3 analysis/perfcounter_width_sequence/analyze_width_sequence_ref_windows.py \
  --sweep-dir "$SWEEP" \
  --reference-csv "$SWEEP/11_SP/SP_chunk001.csv" \
  --widths 128,256,512,1024,2048 \
  --out-dir results/perfcounter_analysis/single_sweep_ref_test
```

Inspect:

```bash
column -s, -t \
  results/perfcounter_analysis/single_sweep_ref_test/reference_width_windows.csv \
  | less -S
```

## B. Analyze repeated sweeps

```bash
python3 analysis/perfcounter_width_sequence/analyze_repeated_width_sweeps.py \
  --sweeps-root results/perfcounter_sweeps/full_sweeps \
  --latest-n 2 \
  --widths 128,256,512,1024,2048 \
  --out-dir results/perfcounter_analysis/repeated_width_sequence_latest2
```

Inspect stable counters:

```bash
python3 - <<'PY'
import pandas as pd

path = (
    "results/perfcounter_analysis/repeated_width_sequence_latest2/"
    "stable_width_scaling_counters.csv"
)

df = pd.read_csv(path)
print(df.head(50).to_string(index=False))
PY
```

## C. Cross-check with local windows

```bash
python3 analysis/perfcounter_width_sequence/analyze_repeated_width_sweeps_local_windows.py \
  --sweeps-root results/perfcounter_sweeps/full_sweeps \
  --latest-n 2 \
  --widths 128,256,512,1024,2048 \
  --out-dir results/perfcounter_analysis/repeated_width_sequence_latest2_local_windows \
  --groups SP,TP,UCHE,HLSQ,RBBM,CP
```

Compare counters found by both methods:

```bash
python3 - <<'PY'
import pandas as pd

ref_path = (
    "results/perfcounter_analysis/repeated_width_sequence_latest2/"
    "stable_width_scaling_counters.csv"
)

local_path = (
    "results/perfcounter_analysis/repeated_width_sequence_latest2_local_windows/"
    "stable_width_scaling_counters.csv"
)

ref = pd.read_csv(ref_path)
local = pd.read_csv(local_path)

keys = ["group", "counter"]

both = (
    ref[keys]
    .drop_duplicates()
    .merge(local[keys].drop_duplicates(), on=keys, how="inner")
    .sort_values(keys)
)

print(both.to_string(index=False))
PY
```

```bash

  --sweep-dir "$SWEEP" \
  --reference-csv "$SWEEP/09_UCHE/UCHE_chunk001.csv" \

  --out-dir results/perfcounter_analysis/reference_debug \

  --pad-samples 10
```

For local-window diagnosis:

```bash
python3 analysis/perfcounter_width_sequence/analyze_width_sequence.py \
  --sweep-dir "$SWEEP" \
  --widths 128,256,512,1024,2048 \
  --out-dir results/perfcounter_analysis/local_detection_debug
```

Then inspect:

# Interpretation guidance

## Strong width scaling

A strong or near-16x counter may represent:

- operations proportional to element count;
- memory requests proportional to data size;
- cacheline traffic;
- shader instructions;
- transactions between GPU blocks; or
- another event directly tied to workload width.

It does not automatically indicate a bottleneck.

## Flat or saturated counters

A flat counter may represent:

- fixed launch overhead;
- a resource already saturated;
- an event independent of width;
- a counter with limited visibility;
- a short capture window; or
- incorrect region alignment.

## Zero counters

A zero counter may mean:

- the event did not occur;
- the selected hardware counter is unsupported or inactive;
- the workload does not use that block;
- the counter was not programmed correctly;
- multiplexing or collection failed; or
- the analysis window missed the activity.

Treat zero counters as diagnostic results, not automatically as unused hardware.

## Bottleneck analysis

Width scaling alone is insufficient to prove a bottleneck.

A stronger bottleneck argument combines:

- increasing stall/starvation/latency counters;
- request or transaction growth;
- cache or memory traffic;
- SP busy versus ALU working cycles;
- stable cross-run behavior;
- benchmark runtime;
- KGSL RAM-wait or bus evidence; and
- controlled benchmark configuration.

# Validation checklist

Before trusting the output:

1. Confirm the benchmark ran widths in the same order as `--widths`.
2. Inspect the reference window CSV.
3. Check that all expected sweeps were discovered.
4. Review skipped-run warnings.
5. Inspect region-detection quality for local-window analysis.
6. Confirm the same counter families appear across repeated runs.
7. Compare reference-window and local-window conclusions.
8. Check that sampling interval and window padding are reasonable.
9. Verify that benchmark configuration is identical across sweeps.
10. Avoid treating classification labels as direct bottleneck proof.

# Maintenance recommendations

1. Treat `analyze_repeated_width_sweeps.py` as the primary supported analyzer.
2. Keep the local-window repeated script as a validation path.
3. Keep `analyze_width_sequence.py` for debugging and historical
   reproducibility.
4. Generalize `make_repro_report.py` before using it for benchmarks other than
   the current fused-softmax experiment.
5. Extract duplicated region detection, summarization, and classification logic
   into a shared Python module.
6. Add explicit checks for empty summary DataFrames before grouping.
7. Add CLI options for classification thresholds.
8. Record sweep configuration and tool version in every analysis output.
9. Prefer content-based run selection over directory modification time for
   reproducibility.
10. Add plots only as a separate reporting layer; keep the core CSV analysis
    deterministic and scriptable.
