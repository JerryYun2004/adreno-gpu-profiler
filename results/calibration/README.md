# Calibration Results

This directory contains working calibration results for the Adreno GPU
performance-counter streamer.

The results are generated by running controlled Vulkan microbenchmarks while
the phone-side streamer records raw KGSL/Adreno counter deltas.

Two calibration families are stored here:

1. **ALU-chain calibration** — increases a dependent integer ALU chain through
   64, 128, 256, and 512 high-level update statements.
2. **Memory-stride calibration** — keeps arithmetic work nearly constant while
   changing the memory address stride through 1, 4, 16, and 64 elements.

The directory is intended to answer:

```text
Does an ALU-related counter scale with controlled ALU work?

Do memory-related counters respond when locality changes while ALU work stays
approximately fixed?
```

These files are outputs from the perf-counter streamer. They are not source
code, shader inputs, executable binaries, or normal perf-counter sweeper output.

## Important naming issue

The files under:

```text
alu_chain/summaries/
```

are **not machine-generated aggregate summaries**.

They still contain:

- streamer counter-selection metadata;
- `GET` register information;
- a CSV data section;
- cleanup messages; and
- the streamer's temporary-file message.

They appear to be a second set of calibration captures, likely retained from the
streamer's device-side temporary output or a separate run.

The directory name `summaries/` is therefore misleading.

A clearer future name would be:

```text
alu_chain/secondary_captures/
```

or:

```text
alu_chain/repeated_runs/
```

Do not rename the directory during the current repository reorganization unless
all path references are checked.

## Direct relationship to the streamer

These files are direct streamer capture logs.

They preserve:

- selected counter names;
- counter group IDs;
- selectors;
- returned low/high registers;
- requested sampling interval;
- elapsed sample time;
- raw counter deltas;
- idle samples;
- active workload samples; and
- some cleanup/output-path messages.

The streamer does not launch the Vulkan workload. The workload must run
separately while the streamer samples the counters.

## Relationship to the sweeper

These are not sweeper directory outputs.

The sweeper normally creates:

```text
sweep_<timestamp>/
├── <group directories>/
├── chunk CSV files
├── benchmark logs
├── run_config.txt
└── summary.csv
```

The calibration files here instead contain a manually selected small counter
set in one stream.

The microbenchmarks can still be used as sweeper workloads in later
experiments. These results validate that selected counters behave sensibly
before a larger counter sweep is interpreted.

The fixed shader variants are:


They keep the following approximately constant:

- element count;
- dispatch repeat count;
- workgroup size;
- input reads;
- output writes; and
- runner behavior.

They change the explicitly unrolled dependent ALU-chain length.

## Memory-stride calibration

The historical runnable stride path uses compile-time stride variants:

```text
mem_stride_1_legacy.comp.spv
mem_stride_4_legacy.comp.spv
mem_stride_16_legacy.comp.spv
mem_stride_64_legacy.comp.spv
```

It keeps the following approximately constant:

- element count;
- loop iteration count;
- dispatch repeat count;
- workgroup size;
- accumulation arithmetic; and
- number of shader loads.

It changes how far each invocation advances through the input array between
iterations.

# Important file-format note

Every file has a `.csv` extension, but none is a strict CSV file from the first
line.

A typical ALU capture begins with:

```text
[selected] 2 counters, interval 0.005 s
...
[GET] SP_BUSY_CYCLES ...
...
elapsed_s,SP_BUSY_CYCLES,SP_ALU_WORKING_CYCLES
...
[cleanup] releasing 2 active counters
...
```

A memory capture begins with a longer six-counter preamble.

Therefore, this usually fails or produces malformed rows:

```python
pandas.read_csv("alu_chain_256_perf_stream.csv")
```

A correct parser must:

1. locate the line beginning with `elapsed_s,`;
2. parse only numeric rows after that header; and
3. ignore cleanup/status lines after the table.

---

# Common capture configuration

All twelve files request:

```text
sampling interval = 0.005 seconds
```

The values are:

```text
counter deltas since the previous sample
```

They are not absolute register values.

The observed sample interval is close to, but not exactly, 5 ms because of:

- process scheduling;
- system-call latency;
- counter-read overhead;
- Android scheduling;
- ADB/shell execution; and
- host output handling.

# ALU-chain calibration

# Experimental expectation

The controlled workload sizes are:

```text
64 : 128 : 256 : 512
 1 :   2 :   4 :   8
```

When normalized to the 256 variant, ideal ALU-counter scaling is:

```text
64  → 0.25
128 → 0.50
256 → 1.00
512 → 2.00
```

The variant number refers to high-level generated update statements, not exact
Adreno machine instructions.

`SP_ALU_WORKING_CYCLES` follows the expected relationship closely:

```text

```

The relative deviation from ideal is approximately:

```text
64:  +1.19%
128: -0.01%
256:  0.00%
512: -0.20%
```

This is strong evidence that:

```text
SP_ALU_WORKING_CYCLES
```

responds linearly to controlled dependent integer ALU work in this benchmark.

## SP busy behavior

`SP_BUSY_CYCLES` also rises strongly, but the smallest variant has more fixed
overhead relative to useful work:

```text

128: 0.517×
256: 1.000×
512: 1.955×
```

This is expected because SP busy time can include:

- dispatch overhead;
- scheduling;
- fixed shader setup;
- input/output operations;
- non-ALU instructions; and
- pipeline activity.

It is less direct than `SP_ALU_WORKING_CYCLES` for this calibration.

# Main memory findings

# 1. ALU work remains almost perfectly controlled

Normalized `SP_ALU_WORKING_CYCLES`:

```text
stride 1:  1.000×
stride 4:  1.000×
stride 16: 1.000×
stride 64: 1.000×
```

The stride-16 and stride-64 totals differ from stride 1 by approximately
0.005%.

This is strong evidence that the arithmetic portion of the workload remained
constant.

# 2. SP busy rises only slightly

Normalized `SP_BUSY_CYCLES`:

```text
stride 1:  1.000×
stride 4:  1.006×
stride 16: 1.014×
stride 64: 1.019×
```

Total SP busy activity increases by only about 1.9% from stride 1 to stride 64.

# 3. UCHE RAM-read requests increase clearly

Normalized `UCHE_RAM_READ_REQ`:

```text
stride 1:  1.000×
stride 4:  1.107×
stride 16: 1.573×
stride 64: 1.887×
```

The stride-64 workload produces about 1.89 times the stride-1 RAM-read requests.

This is the clearest locality-sensitive result in this dataset.

# 4. UCHE busy is strong but non-monotonic

Normalized `UCHE_BUSY_CYCLES`:

```text
stride 1:  1.000×
stride 4:  1.396×
stride 16: 2.266×
stride 64: 1.949×
```

UCHE busy activity peaks at stride 16 rather than stride 64.

Possible contributors include:

- cache behavior;
- request batching;
- latency/throughput balance;
- capture-window differences;
- counter semantics;
- dynamic GPU behavior; and
- ordinary run-to-run variation.

One run per stride is not enough to distinguish these explanations.

# 5. The selected stall counters are inconclusive

Observed `SP_STALL_CYCLES_UCHE` totals:

```text
stride 1:  5,249
stride 4:  14,440
stride 16: 0
stride 64: 0
```

Observed `HLSQ_STALL_CYCLES_UCHE` totals:

```text
stride 1:  1
stride 4:  1
stride 16: 1
stride 64: 1
```

These values are sparse and inconsistent.

They should not be used as primary evidence that the workload did or did not
stall on UCHE.

Possible explanations include:

- unsupported or generation-specific semantics;
- incorrect attribution;
- selector mapping limitations;
- event rarity;
- collection artifacts; or
- the workload not activating these exact countables.

# Correct parser for these files

Use this loader for both the ALU and memory files:

```python
from pathlib import Path
import re

import pandas as pd


def read_streamer_capture(path: str | Path) -> tuple[pd.DataFrame, list[str]]:
    path = Path(path)
    lines = path.read_text(errors="replace").splitlines()

    try:
        header_index = next(
            index
            for index, line in enumerate(lines)
            if line.startswith("elapsed_s,")
        )
    except StopIteration as exc:
        raise ValueError(
            f"No elapsed_s CSV header found in {path}"
        ) from exc

    columns = lines[header_index].split(",")
    rows = []

    for line in lines[header_index + 1:]:
        if not re.match(r"^\d+(?:\.\d+)?,", line):
            continue

        fields = line.split(",")

        if len(fields) != len(columns):
            continue

        try:
            row = [float(fields[0])]
            row.extend(int(value) for value in fields[1:])
        except ValueError:
            continue

        rows.append(row)

    frame = pd.DataFrame(rows, columns=columns)
    preamble = lines[:header_index]

    return frame, preamble
```

This parser ignores:

```text
[cleanup] ...
[csv] samples were recorded ...
```

after the numeric table.

```bash
from pathlib import Path
import re

import numpy as np
import pandas as pd


def load(path):
    lines = path.read_text(errors="replace").splitlines()
    header_index = next(
        i for i, line in enumerate(lines)
        if line.startswith("elapsed_s,")
    )
    columns = lines[header_index].split(",")
    rows = []

    for line in lines[header_index + 1:]:
        if not re.match(r"^\d+(?:\.\d+)?,", line):
            continue

        fields = line.split(",")

        if len(fields) != len(columns):
            continue

        rows.append(
            [float(fields[0])]
            + [int(value) for value in fields[1:]]
        )

    return pd.DataFrame(rows, columns=columns)


def longest_nonzero_region(frame):
    counters = [
        column for column in frame.columns
        if column != "elapsed_s"
    ]

    active = (
        frame[counters]
        .abs()
        .sum(axis=1)
        .ne(0)
        .to_numpy()
    )

    indices = np.flatnonzero(active)

    if len(indices) == 0:
        return frame.iloc[0:0]

    regions = []
    start = previous = int(indices[0])

    for raw_index in indices[1:]:
        index = int(raw_index)

        if index == previous + 1:
            previous = index
        else:
            regions.append((start, previous))
            start = previous = index

    regions.append((start, previous))

    start, end = max(
        regions,
        key=lambda pair: pair[1] - pair[0] + 1,
    )

    return frame.iloc[start:end + 1]


root = Path(
    "results/calibration/memory_stride/raw_streams"
)

rows = []

for stride in [1, 4, 16, 64]:
    path = root / f"mem_stride_{stride}_perf_stream.csv"
    frame = load(path)
    region = longest_nonzero_region(frame)

    row = {
        "stride": stride,
        "start_s": region["elapsed_s"].iloc[0],
        "end_s": region["elapsed_s"].iloc[-1],
        "samples": len(region),
    }

    for counter in frame.columns:
        if counter != "elapsed_s":
            row[counter] = int(region[counter].sum())

    rows.append(row)

summary = pd.DataFrame(rows)
baseline = summary.loc[summary["stride"] == 1].iloc[0]
```

# Recommended run procedure

For formal calibration:

1. verify shader SPIR-V;
2. record shader hash;
3. record runner hash;
4. record streamer hash;
5. enable KGSL counter access;
6. run one warm-up workload;
7. allow the device to settle;
8. start the streamer;
9. run the benchmark;
10. save benchmark stdout/stderr and exit code;
11. stop the streamer;
12. repeat every variant at least three times;
13. rotate run order;
14. record frequency and temperature; and
15. generate derived tables without editing raw captures.

Suggested rotated order:

```text
run set 1:
    64 → 128 → 256 → 512

run set 2:
    512 → 256 → 128 → 64

run set 3:
    128 → 512 → 64 → 256
```

For memory:

```text
run set 1:
    1 → 4 → 16 → 64

run set 2:
    64 → 16 → 4 → 1

run set 3:
    4 → 64 → 1 → 16
```

# What these results support

# ALU calibration

Supported conclusion:

```text
SP_ALU_WORKING_CYCLES scales almost linearly with the controlled ALU-chain
length.
```

This validates the counter for the tested workload and device.

# Memory calibration

Supported conclusion:

```text
The arithmetic work stays essentially constant while UCHE RAM-read requests
increase with larger stride.
```

This demonstrates that the memory experiment changes the memory-system demand
without materially changing ALU work.

---

# What these results do not prove

The files do not prove:

- that every selected counter is correctly mapped;
- that a high counter value identifies the final bottleneck;
- that UCHE RAM-read requests all reached external DRAM;
- that stride 64 is universally slower;
- that the GPU frequency was constant;
- that temperature was identical;
- that the benchmark passed verification;
- that vendor and Turnip behave identically;
- that one run is statistically reproducible;
- that the active-window rule is uniquely correct; or
- that these results generalize to another Adreno generation.

---

# Known limitations

# Hybrid log/CSV format

Standard CSV tools require preprocessing.

# No metadata sidecar

The files do not record the complete benchmark command or hashes.

# One primary run per variant

The raw stream directories contain one capture per parameter value.

# Secondary ALU directory is misnamed

It stores captures, not summaries.

# ALU active regions can be sparse

Short variants contain only a few nonzero samples at a 5 ms sampling interval.

# Memory active-window lengths differ

The number of active samples varies between stride captures.

# Sparse stall counters

The selected SP/HLSQ stall countables do not produce a reliable trend.

# No precise GPU timestamps

`elapsed_s` is streamer host/process time, not a Vulkan timestamp query.

# No thermal/frequency data

Dynamic operating state can influence the results.

# No benchmark logs

Runner verification and exit status are absent.

# Working results versus immutable evidence

Files under `results/` can be regenerated or reorganized. Preserved evidence
should live under `evidence/` with a manifest.
