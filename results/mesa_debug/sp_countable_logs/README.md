# Purpose

The experiment tests the first ten SP countable selectors:

```text
KGSL group:
    0x0a = SP

selectors:
    0 through 9
```

For every selector, the probe attempts to:

1. open `/dev/kgsl-3d0`;
2. request one SP performance counter with `PERFCOUNTER_GET`;
3. record the physical low/high counter-register offsets returned by KGSL;
4. sample the configured counter ten times;
5. calculate deltas between consecutive values;
6. release the counter with `PERFCOUNTER_PUT`; and
7. exit cleanly.

The logs answer several early implementation questions:

```text
Can the KGSL device be opened?

Does group 0x0a accept these selector values?

Does PERFCOUNTER_GET return a usable hardware counter slot?

Can the probe complete its sample loop?

Can the allocated counter be released correctly?

Do values change when the probe runs under the tested conditions?
```

# What each line means

## Opening `/dev/kgsl-3d0`

```text
Opening /dev/kgsl-3d0
```

The probe targets Qualcomm’s KGSL device node for the 3D GPU.

## Open success

```text
open succeeded, fd=3
```

The process obtained a valid file descriptor.

This proves that device-node access succeeded for the execution context used by
the probe.

It does not prove that every KGSL ioctl will be permitted.

## Group and selector

```text
Testing group=0xa countable=N
```

The group is the SP hardware block.

The countable value is the event selector programmed into an available physical
SP performance-counter slot.

The selector is not the physical slot number.

## `PERFCOUNTER_GET` success

```text
PERFCOUNTER_GET succeeded
```

KGSL accepted the request and allocated/configured a counter slot.

This does not prove that the countable will increment for the current workload.

## Returned offsets

```text
returned offset=0x29c offset_hi=0x29d
```

The kernel returned the low/high register identifiers for the allocated physical
counter slot.

These form one logical wide counter value.

## Samples

```text
sample=000 value=0 delta=N/A
sample=001 value=0 delta=0
```

The first sample has no previous value, so its delta is not available.

Later rows compare the current value with the previous sample.

## `PERFCOUNTER_PUT` success

```text
PERFCOUNTER_PUT succeeded
```

The counter allocation was released.

This is important because SP groups have a finite number of physical hardware
counter slots.

# Why every selector returned `0x29c/0x29d`

This is not evidence that selectors 0–9 are the same counter.

The selector and physical counter slot are separate concepts.

```text
selector:
    chooses which event the hardware counter counts

physical slot:
    provides the counter registers that store the selected event's value
```

Each log tests only one selector at a time and releases it before the next run.

KGSL can therefore reuse the first available SP physical counter slot on every
invocation.

In this test sequence:

```text
selector 0 → first available SP slot → 0x29c/0x29d
selector 1 → first available SP slot → 0x29c/0x29d
selector 2 → first available SP slot → 0x29c/0x29d
...
```

When multiple SP counters are active simultaneously, KGSL can allocate different
physical slot/register pairs.

Therefore:

```text
same returned offsets
    expected for sequential one-counter tests

same semantic event
    not implied
```

---

# Why every sample is zero

The logs show that the read loop produced zero for every selector under the
conditions of these tests.

They do **not** identify one definitive cause.

Several explanations are possible.

## 1. No relevant GPU workload was active

SP counters increment only when the GPU executes work that triggers the selected
event.

If the probe ran while the GPU was idle, countables such as:

```text
SP_BUSY_CYCLES
SP_ALU_WORKING_CYCLES
SP_WAVE_CONTEXTS
```

can remain zero.

## 2. The GPU may have power-collapsed between reads

The GPU can enter idle/power-collapse states when no workload is active.

A configured counter does not force useful SP activity.

## 3. Some events are workload-specific

For example:

```text
SP_STALL_CYCLES_TP
```

may remain zero for a compute shader that performs no texture operations.

```text
SP_STALL_CYCLES_RB
```

may remain zero for a compute-only workload with no render-backend dependency.

## 4. Selector 0 is intentionally a zero event

```text
SP_NEVER_COUNT
```

is expected to remain zero.

It acts as a useful negative control.

## 5. The probe may not overlap the workload

A workload that finishes before the first probe sample will not be visible.

## 6. The tested read mechanism may not expose live values correctly

A successful `GET` confirms allocation, not the correctness of the complete
sample path.

This possibility should be tested against a known active workload and compared
with the final streamer.

---

# What the zero values do not mean

The logs do not prove that:

- all SP countables are unsupported;
- all selector mappings are wrong;
- `PERFCOUNTER_GET` failed;
- the returned register pair is invalid;
- the kernel ignored the selector;
- the Adreno GPU lacks these events;
- the final streamer cannot read these counters; or
- selectors 1–9 are equivalent to `NEVER_COUNT`.

Later controlled calibration is needed to distinguish:

```text
valid but idle
valid but workload-specific
configured but unreadable
incorrectly mapped
unsupported
```

# Selector-specific expectations

The following expectations are qualitative and depend on workload, shader stage,
driver behavior, and A8xx counter semantics.

## Selector 0 — `SP_NEVER_COUNT`

Expected:

```text
always zero
```

Use as a negative control.

## Selector 1 — `SP_BUSY_CYCLES`

Expected to increase while the SP block executes shader work.

Good test workload:

```text
long ALU-heavy compute shader
```

## Selector 2 — `SP_ALU_WORKING_CYCLES`

Expected to increase during arithmetic execution.

The dedicated fixed ALU-chain calibration is the strongest test for this
selector.

## Selector 3 — `SP_STALL_CYCLES_VPC_BE`

Expected only when SP experiences relevant VPC-backend stall conditions.

A compute-only shader may produce zero.

## Selector 4 — `SP_STALL_CYCLES_TP`

Expected when SP waits on texture-processor-related activity.

A simple integer ALU shader may produce zero.

## Selector 5 — `SP_STALL_CYCLES_UCHE`

Expected when SP stalls on UCHE-related memory behavior.

A memory-heavy workload is more appropriate than an idle probe.

## Selector 6 — `SP_STALL_CYCLES_RB`

Expected for relevant render-backend dependencies.

A compute workload may not trigger it.

## Selector 7 — `SP_NON_EXECUTION_CYCLES`

May count SP cycles that are not executing useful shader work, depending on the
hardware definition.

Interpret only after workload validation.

## Selector 8 — `SP_WAVE_CONTEXTS`

May count wave contexts or context-related events.

A sufficiently long shader workload should be used.

## Selector 9 — `SP_WAVE_CONTEXT_CYCLES`

May count cycles associated with wave contexts.

It should not be interpreted without comparing it against known shader activity.

# Parse all logs

```bash
cd /Users/jerryyun/adreno-gpu-profiler

from pathlib import Path
import re

root = Path("results/mesa_debug/sp_countable_logs")

print(
    f"{'selector':>8} "
    f"{'offset':>10} "
    f"{'samples':>8} "
    f"{'nonzero':>8} "
    f"{'get':>6} "
    f"{'put':>6}"

for path in sorted(
    root.glob("sp_countable_*.log"),
    key=lambda p: int(
        re.search(r"(\d+)", p.stem).group(1)
    ),
):
    text = path.read_text(errors="replace")

    selector = int(
        re.search(r"countable=(\d+)", text).group(1)
    )

    offset = re.search(
        r"returned offset=(0x[0-9a-f]+)",

    ).group(1)

    values = [
        int(match.group(1))
        for match in re.finditer(r"value=(\d+)", text)
    ]

    print(
        f"{selector:8d} "
        f"{offset:>10s} "
        f"{len(values):8d} "
        f"{sum(value != 0 for value in values):8d} "
        f"{str('PERFCOUNTER_GET succeeded' in text):>6s} "
        f"{str('PERFCOUNTER_PUT succeeded' in text):>6s}"
```

# Create a machine-readable summary

```bash
python3 - <<'PY'
from pathlib import Path
import csv
import re

root = Path("results/mesa_debug/sp_countable_logs")
output = root / "sp_countable_probe_summary.csv"

rows = []

for path in sorted(
    root.glob("sp_countable_*.log"),
    key=lambda p: int(
        re.search(r"(\d+)", p.stem).group(1)
    ),
):
    text = path.read_text(errors="replace")

    selector = int(
        re.search(r"countable=(\d+)", text).group(1)
    )

    offsets = re.search(
        r"returned offset=(0x[0-9a-f]+) "
        r"offset_hi=(0x[0-9a-f]+)",
        text,
    )

    values = [
        int(match.group(1))
        for match in re.finditer(r"value=(\d+)", text)
    ]

    rows.append(
        {
            "file": path.name,
            "group": "0x0a",
            "selector": selector,
            "offset_low": offsets.group(1),
            "offset_high": offsets.group(2),
            "samples": len(values),
            "nonzero_samples": sum(
                value != 0 for value in values
            ),
            "maximum_value": max(values) if values else None,
            "get_succeeded": (
                "PERFCOUNTER_GET succeeded" in text
            ),
            "put_succeeded": (
                "PERFCOUNTER_PUT succeeded" in text
            ),
        }
    )
```

# What the logs do not support

The logs do not establish:

- selector correctness under active GPU work;
- counter linearity;
- counter usefulness;
- workload attribution;
- simultaneous multi-counter allocation;
- counter wrap handling;
- long-duration stability;
- sampling accuracy;
- driver-specific behavior;
- performance bottlenecks; or
- equivalence with Turnip performance queries.

# Known limitations

## No workload metadata

The logs do not state whether any Vulkan workload was active.

## No sample timestamps

The sample interval and total probe duration are not recorded.

## No driver identity

The logs are direct KGSL tests and do not record vendor/Turnip workload context.

## No device metadata

They do not record phone model, Android build, kernel, or GPU revision.

## No tool hash

The exact probe binary is not identified.

## No source revision

The Git commit is not stored.

## No read-path details in the log

The output does not identify every lower-level operation used to obtain the
reported values.

## Single counter at a time

The logs do not test slot exhaustion or simultaneous allocation.

## Only selectors 0–9

The SP selector table contains many additional countables.

## All-zero dataset

The logs are useful for access-path debugging but not for workload
characterization.

## Results directory, not immutable evidence

Files under `results/` can be regenerated or reorganized.

Selected historical logs should be copied under `evidence/` and added to a
manifest when long-term preservation is required.
