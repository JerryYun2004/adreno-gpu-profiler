## Key Discoveries / Findings

The main result is that `SP_ALU_WORKING_CYCLES` scales almost perfectly with the controlled ALU-chain length.

Measured totals:

```text
variant   SP_BUSY_CYCLES   SP_ALU_WORKING_CYCLES   active samples
64        20,501,090       34,089,614              3
128       36,655,209       67,371,008              3
256       70,930,395       134,752,910             7
512       138,636,730      268,970,638             12
```

Normalized against the 256 variant:

```text
alu_chain_64:  measured_ratio = 0.253, ideal_ratio = 0.250
alu_chain_128: measured_ratio = 0.500, ideal_ratio = 0.500
alu_chain_256: measured_ratio = 1.000, ideal_ratio = 1.000
alu_chain_512: measured_ratio = 1.996, ideal_ratio = 2.000
```

This strongly validates that the raw KGSL counter `SP_ALU_WORKING_CYCLES` is measuring meaningful Adreno SP ALU activity.

The SPIR-V integer-operation counts were:

```text
alu_chain_64   → 112 counted SPIR-V integer ops
alu_chain_128  → 224 counted SPIR-V integer ops
alu_chain_256  → 448 counted SPIR-V integer ops
alu_chain_512  → 896 counted SPIR-V integer ops
```

Although the variants are named `64/128/256/512`, the SPIR-V counts are higher because each source-level ALU step lowers to multiple SPIR-V integer operations. Importantly, the instruction counts preserve exact linear scaling.

## Reproduction Steps

### 1. Generate shader variants

From the host repo:

```bash
cd ~/adreno-gpu-profiler/shaders/alu_calibration
python3 generate_alu_chain_variants.py
```

This generates:


### 2. Compile shaders to SPIR-V and dump SPIR-V assembly

```bash
for N in 64 128 256 512; do
  glslangValidator -V -Od -S comp \
    -o alu_chain_${N}.comp.spv \
    alu_chain_${N}.comp

  spirv-dis alu_chain_${N}.comp.spv > alu_chain_${N}.comp.spvasm

  echo "alu_chain_${N}:"
  grep -E "OpIAdd|OpBitwiseXor|OpShiftLeftLogical|OpShiftRightLogical" \
    alu_chain_${N}.comp.spvasm | wc -l
done
```

Observed SPIR-V operation counts:

```text
64   → 112
128  → 224
256  → 448
512  → 896
```

### 5. Analyze the CSV files on the host

```bash
python3 - <<'PY'
import csv
from pathlib import Path

variants = [64, 128, 256, 512]
results = {}

print("variant,busy_total,alu_total,busy_max,alu_max,busy_nonzero,alu_nonzero,samples")

for n in variants:
    path = Path(f"alu_chain_{n}_perf_stream.csv")
    if not path.exists():
        print(f"missing file: {path}")
        continue

    rows = []
    with open(path, newline="") as f:
        for line in f:
            if line.startswith("elapsed_s") or line.startswith("0."):
                rows.append(line)

    samples = list(csv.DictReader(rows))
    if not samples:
        print(f"no CSV samples in: {path}")
        continue

    busy_vals = [int(float(r["SP_BUSY_CYCLES"])) for r in samples]
    alu_vals = [int(float(r["SP_ALU_WORKING_CYCLES"])) for r in samples]

    busy_total = sum(busy_vals)
    alu_total = sum(alu_vals)
    busy_max = max(busy_vals)
    alu_max = max(alu_vals)
    busy_nz = sum(v != 0 for v in busy_vals)
    alu_nz = sum(v != 0 for v in alu_vals)

    results[n] = alu_total

    print(f"{n},{busy_total},{alu_total},{busy_max},{alu_max},{busy_nz},{alu_nz},{len(samples)}")

print()
print("Normalized to alu_chain_256:")
baseline = results.get(256)
if baseline:
    for n in variants:
        if n in results:
            measured = results[n] / baseline
            ideal = n / 256
            print(f"alu_chain_{n}: measured_ratio={measured:.3f}, ideal_ratio={ideal:.3f}")
else:
    print("No alu_chain_256 baseline found.")
PY
```

## Issues / Limitations

* The Vulkan runner `vk_alu_varying_probe` still prints old messages such as:

```text
ALU phases by gid range: 64, 256, 1024, 4096 iterations
```

This message is misleading for the new calibration shaders. In this experiment, the runner is only being used as a generic SPIR-V dispatch wrapper.

* The runner also reports verification failures because its CPU reference function is not updated for the new generated shaders. The GPU dispatch still completes successfully, so the counter measurements remain useful.

* The initial CSV path was accidentally saved under `/data/local/tmp` instead of `/data/local/tmp/jerry_work`. This was corrected. Future outputs should be written directly to `/data/local/tmp/jerry_work`.

* Android shell does not have `python3`, so CSV analysis must be done on the host Mac after `adb pull`, or with shell tools such as `awk`.

* Android `find` does not support `find -ls`; use `find ... -print` or `find ... -exec ls -lh {} \;` instead.

* The SPIR-V operation counts are not exactly equal to the variant labels `64/128/256/512`; however, they preserve exact proportional scaling, which is sufficient for this validation.

A good follow-up is to create a memory-dominated shader family such as:

Then profile them with:


The goal is to confirm that memory-heavy workloads produce different counter behavior from the ALU-chain shaders, especially lower ALU scaling and higher memory-stall or RAM-wait behavior.
