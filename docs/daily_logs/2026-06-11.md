## Key Discoveries / Findings

The main result is that `SP_ALU_WORKING_CYCLES` scales almost perfectly with the controlled ALU-chain length.

Measured totals:

```text
variant   SP_BUSY_CYCLES   SP_ALU_WORKING_CYCLES   active samples
64        20,501,090       34,089,614              3
128       36,655,209       67,371,008              3
256       70,930,395       134,752,910             7
512       138,636,730      268,970,638             12
```

Normalized against the 256 variant:

```text
alu_chain_64:  measured_ratio = 0.253, ideal_ratio = 0.250
alu_chain_128: measured_ratio = 0.500, ideal_ratio = 0.500
alu_chain_256: measured_ratio = 1.000, ideal_ratio = 1.000
alu_chain_512: measured_ratio = 1.996, ideal_ratio = 2.000
```

This strongly validates that the raw KGSL counter `SP_ALU_WORKING_CYCLES` is measuring meaningful Adreno SP ALU activity.

The SPIR-V integer-operation counts were:

```text
alu_chain_64   → 112 counted SPIR-V integer ops
alu_chain_128  → 224 counted SPIR-V integer ops
alu_chain_256  → 448 counted SPIR-V integer ops
alu_chain_512  → 896 counted SPIR-V integer ops
```

Although the variants are named `64/128/256/512`, the SPIR-V counts are higher because each source-level ALU step lowers to multiple SPIR-V integer operations. Importantly, the instruction counts preserve exact linear scaling.

variants = [64, 128, 256, 512]

## Issues / Limitations

* The Vulkan runner `vk_alu_varying_probe` still prints old messages such as:

```text
ALU phases by gid range: 64, 256, 1024, 4096 iterations
```

This message is misleading for the new calibration shaders. In this experiment, the runner is only being used as a generic SPIR-V dispatch wrapper.

* The runner also reports verification failures because its CPU reference function is not updated for the new generated shaders. The GPU dispatch still completes successfully, so the counter measurements remain useful.

* The initial CSV path was accidentally saved under `/data/local/tmp` instead of `/data/local/tmp/jerry_work`. This was corrected. Future outputs should be written directly to `/data/local/tmp/jerry_work`.

* Android shell does not have `python3`, so CSV analysis must be done on the host Mac after `adb pull`, or with shell tools such as `awk`.

* Android `find` does not support `find -ls`; use `find ... -print` or `find ... -exec ls -lh {} \;` instead.

* The SPIR-V operation counts are not exactly equal to the variant labels `64/128/256/512`; however, they preserve exact proportional scaling, which is sufficient for this validation.

## Key Discoveries / Findings

The memory-stride experiment produced a clear contrast against the earlier ALU-chain calibration.

For the ALU-chain shaders, `SP_ALU_WORKING_CYCLES` scaled almost perfectly with the programmed ALU-chain length.

For the memory-stride shaders, `SP_ALU_WORKING_CYCLES` stayed nearly constant, while memory/cache activity increased with stride.

Final measured totals:

```text
stride  samples  SP_BUSY_CYCLES  SP_ALU_WORKING_CYCLES  UCHE_BUSY_CYCLES  UCHE_RAM_READ_REQ
1       169      8,663,257,167   5,381,565,070          280,459,342       34,900,424
4       179      8,716,333,912   5,381,565,070          389,984,495       38,403,772
16      178      8,780,704,191   5,381,292,032          619,375,381       50,431,114
64      175      8,820,830,026   5,381,292,032          552,913,593       67,121,254
```

Normalized ratios:

```text
stride  ALU/BUSY  UCHE_BUSY/BUSY  RAM_READ_REQ/BUSY
1       0.621194  0.032373        0.004029
4       0.617412  0.044742        0.004406
16      0.612854  0.070538        0.005743
64      0.610066  0.062683        0.007609
```

Main observations:

* `SP_ALU_WORKING_CYCLES` stayed almost constant at approximately `5.38e9`.
* `SP_BUSY_CYCLES` increased from approximately `8.66e9` to `8.82e9`.
* `ALU/BUSY` decreased from `0.621` to `0.610`.
* `UCHE_RAM_READ_REQ/BUSY` increased from `0.0040` to `0.0076`.
* `UCHE_BUSY_CYCLES/BUSY` increased strongly from stride 1 to stride 16, then remained elevated at stride 64.

This indicates that increasing stride increases memory/cache-system activity while the programmed ALU work remains nearly unchanged.

The best memory-side indicators in this experiment were:

```text
UCHE_BUSY_CYCLES
UCHE_RAM_READ_REQ
```

The following counters were less useful in this specific workload because they stayed near zero or did not scale clearly:

```text
UCHE_VBIF_READ_BEATS_SP
SP_UCHE_READ_TRANS
SP_STALL_CYCLES_UCHE
HLSQ_STALL_CYCLES_UCHE
```

## Issues / Limitations

* `UCHE_BUSY_CYCLES` and `UCHE_RAM_READ_REQ` showed useful memory-pressure behavior, but not every memory-related counter was useful.
* `UCHE_VBIF_READ_BEATS_SP` and `SP_UCHE_READ_TRANS` stayed near zero and should not be used as primary evidence for this workload.
* `SP_STALL_CYCLES_UCHE` and `HLSQ_STALL_CYCLES_UCHE` also stayed near zero, so they did not provide strong stall evidence in this experiment.
* The memory-stride shader is not intended to verify functional correctness with the original `vk_mem_probe` CPU reference. The `--no-verify` patch is necessary because this experiment uses the runner as a generic SPIR-V dispatch tool.
* The memory-stride experiment shows memory/cache pressure indirectly through UCHE activity and RAM read requests, not through a direct end-to-end DRAM bandwidth measurement.
* The stride 64 case increased `UCHE_RAM_READ_REQ/BUSY` but had slightly lower `UCHE_BUSY/BUSY` than stride 16, so the trend is strong but not perfectly monotonic across every counter.
