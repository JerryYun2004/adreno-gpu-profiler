## Key Discoveries / Findings

* The physical counter capacity is not universal across groups. Different GPU blocks expose different numbers of simultaneously reservable counter slots.
* Observed example capacities:

  * `CP`: 14 counters
  * `TP`: 12 counters
  * `UCHE`: 24 counters
  * `SP`: 24 counters
* `Device or resource busy` during `PERFCOUNTER_GET` means the group’s physical counter slots are full, not necessarily that the counter name is invalid.
* `reg_low` and `reg_high` are the physical 32-bit register IDs assigned by KGSL for the low and high halves of a 64-bit performance counter.
* The sweeper successfully completed a full reduced-size sweep:

  * 141 chunks completed
  * 1200 counters swept
  * all benchmark exit statuses were `0`
* `SP_chunk001.csv` showed the expected shader work completed:

  * `SP_FS_STAGE_WAVE_SAMPLES = 8192` for `rows=256`, `repeats=32`
  * This matches `256 × 32 = 8192`, confirming the benchmark executed the expected number of workgroups.
* The benchmark did not run for the full 2-second recording window. Instead, the GPU work appeared as a short burst, while the sweeper continued recording idle/background activity afterward.
* The current sweeper sweeps **performance counters**, not benchmark sizes. Each chunk reruns the same fixed benchmark configuration.
* The earlier phone crash with larger workload settings was likely caused by memory/system pressure from repeated full sweeps, not a fundamental counter-sweeper logic error.
* To create multiple visible compute bursts, the benchmark needs to be modified or wrapped so that dispatch groups are separated by explicit CPU-side waits, such as `sleep 0.1`.

### 6. Run width sweep manually from host

```bash
for W in 128 256 512 1024 2048; do
  echo "============================================================"
  echo "[host] starting width=${W}"
  echo "============================================================"

  adb shell 'su -c "mkdir -p /data/local/tmp/jerry_work/perfcounter_sweeps_widths"'

  adb shell "su -c \"/data/local/tmp/streamer_sweeper \
    --time 2 \
    --out-root /data/local/tmp/jerry_work/perfcounter_sweeps_widths/width_${W} \
    --bench-args '--width ${W} --rows 256 --repeats 256 --csv'; \
    echo SWEEPER_EXIT_CODE:\$?\""

  ADB_EXIT_CODE=$?

  echo "[host] adb shell exit code for width=${W}: ${ADB_EXIT_CODE}"

  if [ "${ADB_EXIT_CODE}" -ne 0 ]; then
    echo "[host] adb shell failed or phone disconnected/rebooted at width=${W}"
    break
  fi

  echo "[host] finished width=${W}"
  sleep 2
done
```

## Issues / Limitations

* Full all-counter sweeps are heavy because the benchmark is relaunched for every counter chunk.
* Large benchmark sizes or high repeat counts can create memory pressure and may crash or reboot the phone.
* The current sweeper does not yet support selecting only specific groups, such as `SP,UCHE,TP,CP`.
* The current sweeper does not sweep benchmark sizes internally. Width sweeps currently require a host-side shell loop.
* The current benchmark submits repeated dispatches back-to-back in one command buffer, so multiple dispatches appear as one continuous GPU activity burst.
* A 1–2 ms sampling interval is not fine-grained enough to separate tightly packed dispatches.
* Seeing one burst does not mean only one dispatch occurred. In the checked SP data, the total wave count matched the expected number of workgroups.
* The benchmark may finish much earlier than the fixed sweeper recording duration. The remaining CSV samples can represent idle or background GPU activity.
* Some listed XML counters may still be invalid, unsupported, or not useful on this specific GPU/kernel setup. The sweeper should continue skipping failed counters safely.

## Most Likely Next Step

Add a benchmark-side burst mode or wrapper mode to create separated GPU activity windows. The desired structure is:

```text
run burst 1
wait for GPU idle
sleep 0.1 s
run burst 2
wait for GPU idle
sleep 0.1 s
...
```

A useful long-term benchmark interface would be:

```bash
--bursts 10
--burst-repeats 32
--burst-sleep 0.1
```

This would make the SP/UCHE/TP counter traces easier to interpret because each burst would be separated in time instead of being merged into one short activity region.

After that, add targeted sweep options such as:

```bash
--groups SP,UCHE,TP,CP
```

so larger workloads can be profiled without running a full 1200-counter exhaustive sweep every time.
