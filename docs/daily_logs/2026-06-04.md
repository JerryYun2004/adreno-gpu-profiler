# Daily Log — Turnip A8XX Performance Query Investigation

## Date

2026-06-05

## Objective

Today I investigated whether Mesa Turnip could provide a userspace path to access detailed Adreno A8XX hardware performance counters through `VK_KHR_performance_query` on the Adreno 830 / KGSL Android device.

The main question was whether patched Turnip could expose and read raw A8XX counters without modifying the kernel or changing KGSL permissions.

### 6. Added `VkPerformanceQuerySubmitInfoKHR`

I patched the submit path in `vk_perf_read_probe.cpp` to include:

```cpp
VkPerformanceQuerySubmitInfoKHR perf_submit{};
perf_submit.sType = VK_STRUCTURE_TYPE_PERFORMANCE_QUERY_SUBMIT_INFO_KHR;
perf_submit.counterPassIndex = 0;

VkSubmitInfo submit{};
submit.sType = VK_STRUCTURE_TYPE_SUBMIT_INFO;
submit.pNext = &perf_submit;
submit.commandBufferCount = 1;
submit.pCommandBuffers = &cmd;
```

After rebuilding and rerunning, the failure remained:

```text
Read mode WAIT: VkResult=2 value=0
```

This showed that the issue was not simply a missing performance query submit-info structure.

### 9. Isolated the failing command sequence

I added several temporary debug modes to isolate which command caused failure.

#### Availability-only test

This skipped all raw counter programming and only wrote a magic value and availability flag:

```text
result = 0x12345678
availability = 1
```

Result:

```text
Read mode WAIT: VkResult=0 value=305419896
Read mode PARTIAL: VkResult=0 value=305419896
```

This proved:

```text
The query BO is valid.
GPU command-stream writes to the query BO work.
CPU readback works.
The availability mechanism works.
```

#### Barrier-only test

This included `emit_counter_barrier()` but skipped counter select/read operations. It wrote:

```text
result = 0xabcdef01
availability = 1
```

Result:

```text
Read mode WAIT: VkResult=0 value=2882400001
Read mode PARTIAL: VkResult=0 value=2882400001
```

This proved:

```text
emit_counter_barrier() is safe.
WFI / CP_BARRIER is not the failure source.
```

#### Read-only test without selector programming

This skipped the selector write but read from the counter register using `CP_REG_TO_MEM`.

Result:

```text
Read mode WAIT: VkResult=0 value=0
Read mode PARTIAL: VkResult=0 value=0
```

This proved:

```text
CP_REG_TO_MEM from the counter register does not break command execution.
The result is zero because the counter selector was not programmed.
```

#### Select-only test

This wrote the performance-counter selector register but skipped the counter read and instead attempted to write a magic value afterward.

For `counter[3]`, the mapping was:

```text
select_reg = 0x8d3
selector   = 0x3
counter_lo = 0x1b6
```

Result:

```text
Read mode WAIT: VkResult=2 value=0
Read mode PARTIAL: VkResult=0 value=0
PARTIAL+AVAIL: value=0 availability=0
```

This proved that the failure starts when Turnip emits a `PKT4` write to the A8XX performance-counter select register.

### 10. Tested multiple CP selectors

I repeated the select-only test for:

```text
counter[1] = PERF_CP_ALWAYS_COUNT
counter[2] = PERF_CP_BUSY_GFX_CORE_IDLE
counter[3] = PERF_CP_BUSY_CYCLES
```

All three used the same physical counter slot:

```text

```

with different selector values:

```text

```

All three failed in the same way:

```text
Read mode WAIT: VkResult=2 value=0
Read mode PARTIAL: VkResult=0 value=0
availability=0
```

This showed the issue is not one bad selector value. The common failing operation is writing the A8XX CP performance-counter select register from the userspace command stream.

### 11. Inspected relevant Mesa KGSL and A8XX code paths

I inspected Mesa’s KGSL and Turnip code around performance-counter support:

```bash
sed -n '1550,1630p' src/freedreno/vulkan/tu_knl_kgsl.cc
sed -n '1865,1905p' src/freedreno/vulkan/tu_knl_kgsl.cc
sed -n '1788,1810p' src/freedreno/vulkan/tu_device.cc
grep -R "PERFCOUNTER_GET\|PERFCOUNTER_PUT\|PERFCOUNTER_QUERY\|PERFCOUNTER_READ" -n \
  src/freedreno/vulkan src/freedreno/drm-shim src/freedreno/common src/freedreno/perfcntrs
```

Findings:

```text
Turnip KGSL only uses IOCTL_KGSL_PERFCOUNTER_READ for Perfetto timestamp calibration.
No full VK_KHR_performance_query path exists through KGSL PERFCounter GET/READ/PUT.
Mesa normally disables direct selectable performance counters for gen8+.
Mesa comments indicate gen8+ should use kernel UAPI for performance counter management.
```

This matches the observed behavior: forcing the old userspace selector-register path on A8XX/KGSL does not work.

## Key Discoveries / Findings

1. **Turnip can be loaded on the phone using a root bind mount.**

   The active driver changed from the Qualcomm vendor driver to:

   ```text
   turnip Mesa driver
   ```

2. **Patched Turnip can expose `VK_KHR_performance_query`.**

   The extension probe showed:

   ```text
   VK_KHR_performance_query: YES
   ```

3. **A8XX raw counter metadata exists in Mesa.**

   After patching `fd_perfcntrs()` to return A8XX groups, the enum probe reported:

   ```text
   performance counters: 2490
   ```

4. **Counter enumeration works, but real counter measurement does not.**

   Counter names and metadata can be listed, but real values cannot be read.

5. **Query BO writeback is not the problem.**

   Magic-value tests proved that command-stream writes to the query BO and CPU readback both work.

6. **Barriers are not the problem.**

   The barrier-only test passed.

7. **Counter register readback without selector programming does not break execution.**

   `CP_REG_TO_MEM` from the counter register completed and returned zero, as expected without selector setup.

8. **The failure starts at the performance-counter selector write.**

   Writing the A8XX CP select register `0x8d3` causes subsequent result and availability writes not to complete.

9. **Multiple CP selectors fail identically.**

   `PERF_CP_ALWAYS_COUNT`, `PERF_CP_BUSY_GFX_CORE_IDLE`, and `PERF_CP_BUSY_CYCLES` all failed when programmed through the selector register.

10. **Mesa’s source comments explain this behavior.**

Mesa normally disables selectable counters on gen8+ because gen8+ should use kernel UAPI for perf-counter management.

---

## Current Interpretation

The current best interpretation is:

```text
Patched Turnip can expose A8XX raw performance-counter metadata through VK_KHR_performance_query, but current Turnip/KGSL cannot actually read raw A8XX counter values on this device.
```

More specifically:

```text
The existing Turnip raw query execution path still uses direct userspace command-stream writes to performance-counter selector registers.
This path appears unsafe or unsupported on Adreno 830 / KGSL.
Mesa comments indicate A8XX/gen8+ should use KGSL kernel UAPI for performance-counter management.
However, previous direct KGSL ioctl tests showed IOCTL_KGSL_PERFCOUNTER_READ returns EPERM, even as root.
```

Therefore, the likely final conclusion is:

```text
Raw A8XX hardware performance counters are visible in Mesa metadata, but practically inaccessible on this phone without kernel/vendor support or a working privileged KGSL UAPI path.
```

## Issues / Limitations

1. **The Mesa tree currently contains temporary debug instrumentation.**

   The `JERRY_RAW_*` patches were useful for isolating the failure, but they should be cleaned up or placed on a separate debug branch before committing a clean Mesa fork.

2. **The current Turnip raw-query path is not a proper gen8 KGSL UAPI implementation.**

   It still relies on direct userspace command-stream selector-register writes.

3. **The kernel UAPI path may also be blocked.**

   Previous standalone KGSL ioctl probes showed:

   ```text
   PERFCOUNTER_QUERY works
   PERFCOUNTER_GET works
   PERFCOUNTER_READ fails with EPERM
   ```

   This happened even as root.

4. **No real hardware counter value was obtained today.**

   The work successfully narrowed the failure mode, but did not produce usable raw SP/CP/UCHE counter values.

5. **The result applies to this phone/kernel stack.**

   Other devices, kernels, debug builds, or vendor-internal tools may expose different access permissions.

---

## Most Likely Next Step

The practical next step is to stop treating raw hardware counters as the main profiler path for now, and document this as a negative result.

The next project direction should be:

```text
1. Commit the Turnip/A8XX performance-query investigation report.
2. Save the raw logs as evidence.
3. Keep the Mesa patches on an experimental branch.
4. Continue the main profiler using KGSL tracepoints, sysfs nodes, pwrstats, ram_wait, frequency, and bus-level signals.
```

For future research, the next technical follow-up would be:

```text
Inspect the KGSL kernel source to identify the permission check causing IOCTL_KGSL_PERFCOUNTER_READ to return EPERM.
```

However, for the current no-kernel-modification project, the conclusion is clear:

```text
Detailed A8XX hardware performance counters are not practically accessible through the tested Mesa Turnip or direct KGSL userspace paths.
```
