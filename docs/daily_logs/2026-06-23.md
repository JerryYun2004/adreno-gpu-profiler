# Daily Log — ML Primitive Benchmarking and Softmax Width Sweep

## Topic

Vulkan ML primitive benchmarking on Adreno 830 using RMSNorm and softmax variants with KGSL performance counters.

## Tasks Completed

* Built and ran Vulkan compute benchmarks for ML primitives on the phone.
* Verified RMSNorm and three softmax implementations:

  * three-pass softmax
  * online softmax
  * fused/shared-memory softmax
* Ran reduction-width sweeps across:

```bash
WIDTHS="128 256 512 1024 2048"
```

* Tuned benchmark sizes to make each width long enough for performance-counter sampling without crashing the phone.
* Collected runtime, throughput, estimated bandwidth, and CSV perf-counter logs for each benchmark.
* Re-enabled and validated the fused/shared-memory softmax path after confirming it passes correctness tests.
* Started investigating how to connect throughput trends with detailed performance counters.

## Key Discoveries / Findings

* RMSNorm ran correctly across all tested widths after using adaptive repeats.
* RMSNorm throughput improved strongly from width 128 to 512/1024, then slightly dropped at width 2048.
* A too-large RMSNorm run caused `VK_ERROR_DEVICE_LOST` at:

```text
width=1024, rows=4096, repeats=4096
```

* Reducing repeats fixed the issue:

  * width 1024 passed with repeats 2048
  * width 2048 passed with repeats 1024
* Three-pass softmax showed clear throughput improvement as reduction width increased, peaking around width 1024.
* Online softmax was faster than three-pass at smaller and medium widths, but the advantage became small at larger widths.
* Fused/shared-memory softmax worked correctly, but was slower overall than both three-pass and online softmax.
* The fused version likely reduces global memory traffic, but adds shared-memory traffic, barriers, and possible occupancy pressure.
* Runtime and elements/s are fair for comparing variants, while estimated bandwidth is only a rough metric because the estimated bytes per element differ between implementations.

## Issues / Limitations

* One aggressive RMSNorm configuration caused `VK_ERROR_DEVICE_LOST`:

```text
width=1024, rows=4096, repeats=4096
```

* Adaptive repeats are needed for large widths to avoid GPU instability.
* Estimated bandwidth is based on simplified bytes-per-element assumptions and does not capture all traffic, especially shared/local memory traffic.
* Fused/shared-memory softmax is not directly comparable using estimated bandwidth alone because it trades global memory traffic for local/shared memory traffic and synchronization.
* Performance-counter data has been collected, but the detailed analysis is still in progress.
* Need to inspect shader disassembly to understand instruction count and compiler behavior across variants.
